| | |
|---|---|
| Статус | Реализовано (MVP) |
| Код | этот репозиторий |

## 1. Контекст

Маркетплейс цифровых товаров соединяет покупателей и продавцов, которые не доверяют друг другу.
Площадка берёт на себя безопасность сделки: деньги покупателя замораживаются при оплате и уходят продавцу
только после того, как покупатель подтвердил получение товара.

Главный риск домена — деньги. Ошибка в учёте (двойное списание, списание в минус, потерянный перевод)
стоит дороже любой задержки, поэтому корректность важнее скорости и доступности вспомогательных функций.

## 2. Цели и не-цели

**Цели**

1. Корректный учёт денег при конкурентных запросах и повторах: ни двойного списания, ни отрицательного баланса.
2. Повтор запроса оплаты (таймаут, ретрай клиента) безопасен.
3. События о сделках надёжно доходят до других систем (уведомления, аналитика), даже если брокер временно недоступен.
4. API масштабируется горизонтально; отказ одного инстанса не виден клиентам.
5. Вспомогательные системы (Redis, Kafka, ClickHouse) могут отказать без остановки приёма оплат.
6. Узкие места видны по метрикам до того, как станут инцидентом.

**Не-цели (MVP)**

- Интеграция с реальным эквайрингом, пополнение и вывод средств.
- Споры, арбитраж, возвраты, таймауты автоподтверждения.
- Аутентификация и авторизация пользователей (сейчас любой вызов может действовать от имени любого счёта).
- Мультивалютность.
- Kubernetes, TLS, отказоустойчивость самой базы (реплики, failover).

## 3. Архитектура

```
                    ┌──────────────── входной трафик ────────────────┐
клиент ──► nginx ──►│ haproxy ──► deals (N реплик, stateless)        │
          (:8080)   │                 │  rate limit ◄──► Redis        │
                    │ /analytics/ ──► analytics ◄──► Redis (кэш)      │
                    └─────────────────┼──────────────────▲───────────┘
                                      │ одна транзакция    │ SQL
                                      ▼                    │
                              PostgreSQL                ClickHouse
                     accounts, deals, payments,       deal_events
                     outbox, notifications                 ▲
                                      │                    │ Kafka engine + MV
                                      ▼                    │
                                    relay ──► Kafka deals.events ──► notifications ──► notifications (PG)
                                                                          └─ 3 попытки ─► deals.events.dlq
```

| Компонент | Ответственность | Хранит состояние |
|---|---|---|
| `deals` | API счетов и сделок, транзакции с деньгами, запись событий в outbox | нет (всё в PostgreSQL) |
| PostgreSQL | источник истины: балансы, сделки, оплаты, outbox | да |
| `relay` | публикация outbox в Kafka | нет |
| Kafka | доставка событий потребителям, буфер при их недоступности | да |
| `notifications` | уведомления продавцу | нет (всё в PostgreSQL) |
| ClickHouse | аналитическое хранилище событий | да |
| `analytics` | API агрегатов (GMV, топ продавцов) | нет |
| Redis | счётчики rate limit, кэш аналитики | только временное |
| nginx | единая точка входа, защита от флуда, маршрутизация | нет |
| haproxy | балансировка между репликами, health checks | нет |

## 4. Модель данных

```sql
accounts (id, balance, held)                 -- CHECK (balance >= 0), CHECK (held >= 0)
deals    (id, buyer_id, seller_id, amount, status, created_at, updated_at)
                                             -- status: created → paid → completed
payments (idempotency_key PK, deal_id UNIQUE)
outbox   (id bigserial, type, payload jsonb, created_at, published_at)
```

- **Деньги** — `bigint` в копейках, в API отдаются строкой. Ни `float`, ни `numeric` в JS-числах: исключаем ошибки округления
  и потерю точности после 2^53.
- **`held`** — замороженные под сделки средства. Инвариант: `balance + held` покупателя уменьшается только при подтверждении сделки,
  а сумма `balance + held` по всем счетам меняется только при создании счёта.
- **`payments`** — одна запись на сделку. Две уникальности решают две разные задачи:
  `idempotency_key` — повтор того же запроса, `deal_id` — вторая оплата той же сделки другим ключом.
- **`outbox`** — события пишутся в той же транзакции, что и изменение данных. Частичный индекс по неопубликованным
  держит выборку relay быстрой при любом размере таблицы.

## 5. Ключевые сценарии

### 5.1. Оплата сделки

Одна транзакция PostgreSQL (уровень изоляции `READ COMMITTED`):

1. `INSERT INTO payments (idempotency_key, deal_id) ON CONFLICT DO NOTHING`.
   Если вставка не прошла:
   - ключ уже есть для этой сделки → это повтор, вернуть текущее состояние сделки;
   - ключ есть для другой сделки → 409;
   - ключа нет, но сделка уже оплачена → 409.

   Параллельная вторая оплата той же сделки блокируется на уникальном индексе `deal_id`
   до коммита или отката первой — это и есть сериализация оплат одной сделки.
2. `SELECT … FROM deals WHERE id = $1 FOR UPDATE` — блокировка строки сделки, проверка статуса `created`.
3. `UPDATE accounts SET balance = balance - $amount, held = held + $amount WHERE id = $buyer AND balance >= $amount`.
   0 строк → 422 «недостаточно средств», транзакция откатывается вместе с записью в `payments`, ключ можно использовать снова.
4. `UPDATE deals SET status = 'paid'` и `INSERT INTO outbox ('DealPaid', …)`.
5. `COMMIT`.

Почему так, а не иначе:

- **Условное списание** (`WHERE balance >= amount`) атомарно проверяет и меняет баланс в одном выражении.
  Два параллельных списания с одного счёта сериализуются блокировкой строки, второй увидит уже уменьшенный баланс.
  `CHECK (balance >= 0)` — последняя линия защиты на случай ошибки в коде.
- **Не `SERIALIZABLE`**: нужные гарантии дают блокировки строк и уникальные индексы, а `SERIALIZABLE` добавил бы
  ошибки сериализации под нагрузкой и необходимость ретраев на клиенте.
- **Не распределённая блокировка в Redis**: она не даёт гарантий при паузах процесса и сбоях Redis,
  а источник истины всё равно в PostgreSQL. Блокировка там же, где данные, — проще и надёжнее.

Проверено тестами: 20 параллельных оплат одной сделки разными ключами — успешна ровно одна;
10 параллельных оплат разных сделок при балансе на 3 — успешны ровно 3, баланс не уходит в минус.

### 5.2. Подтверждение сделки

Одна транзакция: `FOR UPDATE` на сделку, проверка статуса `paid`, `held -= amount` у покупателя,
`balance += amount` у продавца, статус `completed`, событие `DealCompleted` в outbox.

### 5.3. Доставка событий

1. **Relay** в цикле берёт до 100 неопубликованных событий: `SELECT … FOR UPDATE SKIP LOCKED ORDER BY id`,
   отправляет пачку в `deals.events` идемпотентным продюсером (`acks=all`), помечает `published_at`, коммитит.
   Нет событий — пауза 500 мс.
2. **Ключ сообщения — id сделки**: события одной сделки попадают в одну партицию и читаются по порядку.
3. **Гарантия at-least-once**: если отправка прошла, а коммит в PostgreSQL упал, пачка уйдёт ещё раз.
   Поэтому каждый потребитель обязан быть идемпотентным; `event-id` (id строки outbox) передаётся в заголовке.
4. **notifications** пишет уведомление с `ON CONFLICT (event_id) DO NOTHING`. При ошибке — 3 попытки
   с экспоненциальной задержкой, затем сообщение уходит в `deals.events.dlq` с заголовками `error` и `attempts`.
   Offset коммитится только после успешной обработки или успешной записи в DLQ — сообщение не теряется.
5. **ClickHouse** читает топик сам (Kafka engine), материализованное представление пишет в `ReplacingMergeTree`
   с ключом `(event_type, event_id)` — дубли схлопываются, запросы используют `FINAL`.
   Битые сообщения не блокируют чтение (`kafka_handle_error_mode = 'stream'`, фильтр по `_error`).

## 6. Рассмотренные альтернативы

| Решение | Альтернатива | Почему выбрали так |
|---|---|---|
| Transactional outbox | Писать в Kafka прямо из обработчика запроса | Двойная запись: БД закоммитилась, Kafka недоступна — событие потеряно. Или наоборот: событие ушло, транзакция откатилась |
| Outbox + relay с поллингом | CDC (Debezium, логическая репликация) | Debezium — ещё один кластер в эксплуатации. Поллинг с частичным индексом проще и даёт задержку до 0,5 с, чего достаточно |
| Идемпотентность в PostgreSQL | Ключи идемпотентности в Redis | Проверка ключа и списание должны быть в одной транзакции, иначе между ними есть окно для гонки |
| Kafka | RabbitMQ | Нужно перечитывать историю (новый потребитель — аналитика — читает с начала) и порядок по ключу |
| ClickHouse через Kafka engine | Отдельный консьюмер на Node, пишущий в ClickHouse | Меньше кода и сервисов; ClickHouse сам пишет пачками, что ему и нужно |
| Retry в памяти консьюмера | Отдельные retry-топики с задержкой | Проще. Минус: на время задержек партиция стоит. Приемлемо при коротких сбоях (см. риски) |
| Fail-open rate limiter | Fail-closed | Лимитер защищает от перегрузки, а не деньги. Отказ Redis не должен останавливать приём оплат |
| Фиксированное окно лимита | Sliding window (sorted set) | Одна атомарная операция вместо нескольких. Минус: на стыке окон проходит до 2× лимита |
| haproxy за nginx | Только nginx | haproxy даёт активные health checks, обнаружение реплик через DNS и подробную статистику; nginx остаётся точкой входа и защитой от флуда |

## 7. Отказы и деградация

| Что отказало | Что происходит | Что видит клиент |
|---|---|---|
| Одна реплика `deals` | haproxy выводит её после 2 неудачных health checks (≈ 4 с) | Ничего; запрос в момент падения может оборваться |
| PostgreSQL | `/health` отвечает 503, все реплики выводятся из балансировки | 503 на всё. Принимать оплаты без источника истины нельзя |
| Kafka | Relay не может отправить, события копятся в outbox (`outbox_unpublished` растёт) | Ничего; уведомления и аналитика отстают и догоняют после восстановления |
| Консьюмер уведомлений | Растёт consumer lag | Уведомления приходят с задержкой |
| ClickHouse | Аналитика отвечает ошибкой; Kafka хранит события, ClickHouse дочитает их | Ошибка только в `/analytics/*` |
| Redis | Каждая команда падает за 300 мс; лимитер пропускает запросы, кэш не используется | +≈0,3 с к запросу, лимиты не действуют |
| Битое сообщение в топике | Консьюмер — в DLQ после 3 попыток; ClickHouse — пропускает | Ничего |

## 8. Масштабирование и производительность

- `deals`, `analytics`, `notifications` — stateless. `deals` масштабируется командой `docker compose up -d --scale deals=N`;
  haproxy (`server-template` + DNS) и Prometheus (`dns_sd_configs`) находят реплики сами.
- Число соединений: `PG_POOL_MAX × число реплик` должно быть меньше `max_connections` PostgreSQL.
  Сейчас 30 × N при `max_connections = 300`. Дальше — PgBouncer в режиме transaction pooling.
- Нагрузочный тест (подробно — [REPORT.md](../loadtest/REPORT.md)): потолок последовательно упирался в пул соединений,
  затем в CPU процесса Node, затем в CPU стенда. 1 600 → 2 457 запросов/с без ошибок.
- Аналитика: запросы с `FINAL` дороже обычных, поэтому результаты кэшируются в Redis на 30 с.
- Масштабирование Kafka-потребителей ограничено числом партиций (3 у `deals.events`).

## 9. Наблюдаемость

| Сигнал | Метрика | На что указывает |
|---|---|---|
| Латентность и ошибки API | `http_request_duration_seconds` по маршруту и статусу | Деградация, всплеск 4xx/5xx |
| Результаты оплат | `deal_payments_total{result}` | Рост 409/422 — проблема клиентов или атака |
| Очередь за соединением | `pg_pool_waiting` | Пул мал или база тормозит — первое узкое место по тесту |
| Нагрузка на процесс | `nodejs_eventloop_lag_p99_seconds`, `process_cpu_seconds_total` | Реплика упёрлась в CPU — пора добавлять реплики |
| Доставка событий | `outbox_unpublished`, `kafka_consumergroup_lag` | Relay или потребитель не успевает, Kafka недоступна |
| Балансировка | `haproxy_server_status`, `haproxy_server_current_sessions` | Реплика выведена, неравномерная нагрузка |

Каждый ответ содержит `X-Request-Id` (его же пишет лог nginx) и `X-Served-By` (реплика) — по ним запрос находится в логах.

## 10. Безопасность

Есть:

- Все SQL-запросы параметризованы, в ClickHouse — через `query_params`.
- Валидация входа: UUID в путях, положительные целые суммы, даты и `limit` в аналитике.
- `X-Forwarded-For` перезаписывается в nginx — клиент не подделает свой IP, чтобы обойти лимит.
- Ограничение тела запроса (16 КБ) и частоты запросов на двух уровнях: nginx (флуд) и приложение (бизнес-лимит).
- Контейнер приложения работает не от root.

Нет (нужно до продакшена):

- **Аутентификация и авторизация**: сейчас любой может оплатить или подтвердить чужую сделку. Нужны JWT
  и проверка, что оплачивает покупатель, а подтверждает именно он.
- TLS на входе, секреты не в `docker-compose.yml`.
- Аудит-лог операций с деньгами.

## 11. Риски и следующие шаги

| Риск | Влияние | План |
|---|---|---|
| Нет аутентификации | Критическое: операции от имени чужого счёта | JWT, проверка владельца на каждой операции |
| Один экземпляр relay | При падении события копятся, но не теряются; при двух экземплярах может нарушиться порядок | Advisory lock или лидер-выборы, чтобы держать несколько экземпляров в горячем резерве |
| Retry в памяти блокирует партицию | Долгий сбой зависимости останавливает обработку всей партиции | Отдельные retry-топики с задержкой |
| Транзакция оплаты — 7 сетевых переходов | Держит соединение дольше нужного, ограничивает пропускную способность | Объединить в один запрос с CTE |
| Нет миграций | Схема применяется целиком при старте, изменения существующих таблиц так не выкатить | node-pg-migrate или аналог |
| Бизнес-логика в сервисе вместе с SQL | Сложнее тестировать правила домена отдельно от базы | Выделить слои domain / application / infrastructure (Clean Architecture) по мере роста правил |
| Дубли в ClickHouse на границе месяцев | Один дубль может не схлопнуться | Брать время события из outbox, а не из Kafka |

Ближайшие функции домена: споры и арбитраж, автоподтверждение по таймауту, возвраты.
Каждая — новый переход в машине состояний сделки и новое событие в outbox; текущая архитектура это поддерживает без изменений.
