# Нагрузочный тест: полный цикл сделки

## Методика

- **Сценарий** (`loadtest/deal-flow.js`): на одну итерацию — 2 счёта, сделка, оплата, подтверждение = 5 POST-запросов.
  Каждая оплата — транзакция с `FOR UPDATE`, условным списанием и записью в outbox.
- **Нагрузка**: k6 `constant-arrival-rate` — фиксированное число сделок в секунду, 30 с на прогон.
  Если сервис не успевает, k6 не запускает новые итерации (`dropped_iterations`) — это и есть признак потолка.
- **Цель**: haproxy в обход nginx — измеряем сервис, а не защиту от флуда. Rate limit приложения отключён (`RATE_LIMIT=10000000`).
- **Пороги**: ошибок < 1%, p95 оплаты < 200 мс, `dropped_iterations` < 10.
- **Стенд**: весь стек (k6, PostgreSQL, Kafka, ClickHouse, Redis, haproxy, nginx, Prometheus, реплики API) на одной машине, 12 ядер, 14 ГБ.
- Сырые выводы k6 — в `loadtest/results/`.

## Поиск узких мест

### 1. Пул соединений PostgreSQL (исправлено)

При 600 сделках/с потолок — около 1 600 запросов/с, p95 вырос в 6 раз. Метрики под нагрузкой:

- `pg_pool_waiting` ≈ **480** запросов в очереди за соединением в каждой реплике, `pg_pool_total` = 10 (значение по умолчанию в `pg`);
- event loop lag p99 ≈ 15 мс — Node не перегружен;
- PostgreSQL ≈ 2,3 ядра из 12 — база не упирается в CPU;
- в `pg_stat_activity` 15 соединений `idle in transaction`: транзакция открыта и ждёт следующей команды от клиента.

**Вывод**: запросы стоят в очереди за соединением, а не в базе. Транзакция оплаты — около 7 сетевых переходов
(`BEGIN`, вставка в `payments`, `SELECT … FOR UPDATE`, списание, смена статуса, outbox, `COMMIT`), и всё это время соединение занято.

**Исправление**: размер пула настраивается (`PG_POOL_MAX`), по умолчанию 30.
Результат: **1 600 → 1 969 запросов/с (+23%)**, p95 оплаты при 600 сделках/с — 781 → 624 мс.

Цена: при 300 сделках/с p95 немного вырос (124 → 167 мс) — больше одновременных транзакций конкурируют
внутри PostgreSQL. Пул нельзя увеличивать бесконечно: сумма пулов всех реплик должна быть меньше
`max_connections` (поднят до 300), иначе нужен PgBouncer.

### 2. CPU процесса Node (решается горизонтальным масштабированием)

После увеличения пула в очереди по-прежнему ~460 запросов, но картина другая:

- `rate(process_cpu_seconds_total)` ≈ **1,09** — каждая реплика полностью занимает одно ядро (event loop однопоточный);
- в PostgreSQL 40 соединений `idle in transaction` с ожиданием `ClientRead` — база ждёт Node, а не наоборот.

**Вывод**: потолок — CPU одного процесса Node. Сервис stateless, поэтому лечится добавлением реплик.
`deals` переделан в масштабируемый сервис: `docker compose up -d --scale deals=4`, haproxy (`server-template` + DNS Docker)
и Prometheus (`dns_sd_configs`) находят реплики сами, правка конфигов не нужна.

Результат: 4 реплики — **2 457 запросов/с**, p95 оплаты 549 мс при попытке дать 900 сделок/с.

### 3. CPU всей машины (предел стенда)

С 4 репликами прирост меньше ожидаемого. Причина — сам стенд:

- load average **17,6** на 12 ядрах, простой CPU **5,5%**;
- на тех же ядрах работают k6 (~1 ядро), PostgreSQL (~2,6), Kafka (~1,2), haproxy, ClickHouse и 4 реплики по ~1 ядру.

Дальше масштабировать на одной машине нельзя: реплики конкурируют за CPU с базой и генератором нагрузки.
Для честного измерения нужны отдельные хосты для k6, базы и API.

## Что ещё можно улучшить

1. **Меньше сетевых переходов в транзакции оплаты.** Объединить 5 запросов в один SQL-запрос с CTE:
   соединение будет занято один переход вместо семи — снизит и нагрузку на пул, и CPU Node на сериализацию.
2. **PgBouncer** в режиме transaction pooling — чтобы реплик было много, а соединений с PostgreSQL мало.
3. **Профилирование Node** (`--cpu-prof`, flame graph) — понять, сколько CPU уходит на NestJS, `pg`, prom-client и rate limiter
   (каждый запрос делает `MULTI` в Redis).
4. **Отдельные хосты** для генератора нагрузки и базы — чтобы измерять сервис, а не соседство на одной машине.

## Как воспроизвести

```bash
RATE_LIMIT=10000000 docker compose up -d --build --scale deals=4
docker compose run --rm -e RATE=600 -e DURATION=30s k6
# дашборд во время прогона: http://localhost:3000 (Grafana), метрики: http://localhost:9090
```
